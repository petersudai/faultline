## Summary
This PR fixes a type-safety issue where `c.body()` was not properly tracking status codes in union types, causing type inference to lose information about multiple possible response statuses. The fix adds generic type parameters to the `BodyRespond` interface and casts the return value to ensure TypeScript correctly infers the status code.

## Findings (3)

### 🟡 Medium — src/context.ts:735 — other

The `body()` method now casts its return value to `ReturnType<BodyRespond>`. While this is necessary for type inference, the cast bypasses TypeScript's type checking. If the actual runtime return type differs from what the generic types promise, the cast could hide a real bug. The cast is applied after calling `#newResponse()`, which returns a plain `Response` object, not a `Response & TypedResponse<...>` intersection.

→ Check: Verify that `#newResponse()` actually returns a Response object that is compatible with the `TypedResponse` intersection type being cast to. Confirm that the status code and data type information are correctly preserved through the method call chain.

### 🟢 Low — src/context.test.ts:154 — test-gap

The test at line 150-159 was modified to call `c.body('Hi')` twice (lines 154 and 157) instead of reusing the first response object. While this tests the intended behavior (that multiple calls to `c.body()` don't override headers), it changes the test semantics. The original test checked that `c.res` (the internal response object) was updated correctly; the new test checks that a fresh call to `c.body()` sees the cleared header. Both are valid, but the change in test intent should be verified.

→ Check: Confirm that the new test still validates the original concern: that calling `c.body()` multiple times correctly applies header changes from `c.header()` calls in between.

### 🟢 Low — src/types.test.ts:2328 — test-gap

The new type test at lines 2328-2346 validates that `c.body()` correctly infers a union of status codes (204 | 201 | 200) when used in different branches. This is a good test for the fix, but it only tests the type inference, not the runtime behavior. There is no runtime test confirming that the actual status codes returned are correct.

→ Check: Consider adding a runtime test (in addition to the type test) that verifies the actual HTTP status codes returned by `c.body()` in the different branches match the inferred types.
