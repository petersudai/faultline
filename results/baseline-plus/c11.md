## Summary
This PR adds support for greedy regex pattern matching with subsequent static path components in the router. It modifies pattern matching logic in TrieRouter and LinearRouter to use lookahead assertions when a greedy pattern is followed by a static component, and introduces a queue-based mechanism to defer matching of nodes that follow greedy captures. The feature is well-tested but has some edge cases and implementation concerns.

## Findings (7)

### 🟡 Medium — src/router/trie-router/node.ts:180 — unhandled-edge-case

The code counts slashes in the matched greedy pattern to determine queue depth: `const componentCount = m[0].match(/\//)?.length ?? 0`. This assumes the matched string contains only forward slashes as path separators. If a parameter value itself contains encoded slashes or other edge cases, this count could be incorrect, causing nodes to be queued at the wrong depth and potentially matching wrong paths.

→ Check: Verify that parameter values cannot contain unencoded slashes, or add explicit validation/escaping. Test with URL-encoded slashes in parameter values.

### 🟡 Medium — src/utils/url.ts:62 — api-contract

The `getPattern` function signature changed to accept an optional `next` parameter, and the cache key now includes `next` (e.g., `${label}#${next}`). This changes the return value's first element from the original label to a cache key when `next` is provided (e.g., `:id{[0-9]+}#next` instead of `:id{[0-9]+}`). Callers that depend on the first element being the original label string may break.

→ Check: Search codebase for all uses of `getPattern()[0]` to ensure they handle the new cache-key format correctly. Verify that the first element is only used for caching/comparison, not for user-facing output.

### 🟡 Medium — src/router/trie-router/node.ts:48 — other

The `key` variable is computed as `Array.isArray(pattern) ? pattern[0] : p`, but `pattern[0]` can now be a cache key like `:id{[0-9]+}#next` instead of the original label. This means different routes with the same label but different next components will have different keys in `#children`, potentially creating duplicate nodes for the same logical parameter.

→ Check: Verify that routes like `/:id{[0-9]+}/a` and `/:id{[0-9]+}/b` don't create separate child nodes for `:id{[0-9]+}`. Test that parameter extraction still works correctly when the same greedy pattern is used with different subsequent components.

### 🟡 Medium — src/router/trie-router/node.ts:206 — unhandled-edge-case

The queue mechanism uses `curNodesQueue.shift()` to pop from the front, but nodes are pushed at index `componentCount`. If `componentCount` is large and multiple greedy patterns match at different depths, the queue array could become sparse or the shift/push logic could cause nodes to be processed out of order or skipped entirely.

→ Check: Test with deeply nested paths and multiple greedy patterns at different levels (e.g., `/:a{.+}/x/:b{.+}/y/:c{.+}/z`). Verify that all matching handlers are found and in the correct order.

### 🟢 Low — src/router/reg-exp-router/router.test.ts:15 — test-gap

Two test cases for 'Capture complex multiple directories' are skipped for RegExpRouter with reason 'UnsupportedPath'. This suggests the feature doesn't work with RegExpRouter, but there's no explanation of why or whether this is a known limitation that should be documented.

→ Check: Add a comment explaining why these tests are unsupported for RegExpRouter, or consider implementing support if feasible. Document this limitation in the router's JSDoc.

### 🟢 Low — src/router/linear-router/router.ts:90 — other

The lookahead logic checks `next[1] !== ':' && next[1] !== '*'` to determine if a lookahead is needed. This assumes `next` is a string with at least 2 characters. If `next` is a single character or empty, this could cause an error or unexpected behavior.

→ Check: Verify that `next` is always a valid path component with at least 2 characters when it's not null/undefined. Add defensive checks if needed.

### 🟢 Low — src/utils/url.ts:66 — other

The lookahead pattern is constructed as `^${match[2]}(?=/${next})`, which assumes `next` is a literal string that doesn't need regex escaping. If `next` contains regex special characters (e.g., `.`, `*`, `+`), the lookahead will not work as intended.

→ Check: Test with path components containing regex special characters (e.g., `/:id{[0-9]+}/file.txt` where `file.txt` contains a dot). Consider escaping `next` before inserting it into the regex.
