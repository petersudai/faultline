## Summary
This PR reorders parameters in the `compose()` function signature (swapping `onError` and `onNotFound`) and implements error handler propagation when mounting sub-apps via `app.route()`. The main risk is that the parameter reordering is a breaking change to the public API that could silently break existing callers who pass positional arguments.

## Findings (6)

### 🔴 High — src/compose.ts:10 — breaking-change

The `compose()` function signature changed from `(middleware, onNotFound?, onError?)` to `(middleware, onError?, onNotFound?)`. This is a breaking change to a public API. Any external code calling `compose(handlers, notFoundFn, errorFn)` with positional arguments will now pass the notFound handler to the error parameter and vice versa, causing silent behavioral corruption.

→ Check: Search the codebase and any known dependents for direct calls to `compose()` with positional arguments. Verify all call sites have been updated. Consider if this should be a major version bump or if the parameter order should be reverted for backward compatibility.

### 🔴 High — src/hono.ts:124 — api-contract

The logic at line 125 checks `app.errorHandler === errorHandler` to decide whether to wrap the handler with compose. This identity check is fragile: it assumes the default errorHandler reference is never reassigned. If a sub-app's errorHandler is set to a function with identical behavior but a different reference, the check will fail and the handler won't be wrapped. Additionally, this only wraps for errorHandler but not for notFoundHandler, creating asymmetry in how custom handlers are propagated.

→ Check: Verify that the identity check `app.errorHandler === errorHandler` is reliable across all scenarios. Consider whether notFoundHandler should also be wrapped when custom. Add a test case where a sub-app's errorHandler is set to a different function reference with the same behavior.

### 🟡 Medium — src/hono.ts:127 — unhandled-edge-case

When wrapping a handler with `compose([r.handler], app.errorHandler)`, only the errorHandler is passed; the notFoundHandler is omitted. This means if a route in the sub-app doesn't return a response, the parent app's notFoundHandler will be used instead of the sub-app's. The test at line 1031 expects '/sub/implicit-404' to be handled by the app (parent), but this behavior may not be intentional or documented.

→ Check: Clarify the intended behavior: should sub-app notFoundHandlers be propagated to parent routes? Review test case at line 1031 and confirm the expected behavior is correct. Consider whether both errorHandler and notFoundHandler should be wrapped together.

### 🟡 Medium — src/compose.test.ts:158 — test-gap

Test calls updated to pass `undefined` as the second parameter (onError) and onNotFound as the third. While the tests pass, there's no test explicitly verifying that swapping the parameter order would break old code, or that the new order is correct. The test suite doesn't validate backward compatibility concerns.

→ Check: Add a test that explicitly verifies the parameter order is correct by passing both onError and onNotFound and confirming each is called in the right scenario. Consider adding a deprecation notice or migration guide if this is a public API.

### 🟡 Medium — src/hono.ts:246 — api-contract

The call to `compose()` at line 246 now passes `this.errorHandler` as the second parameter and `this.notFoundHandler` as the third, matching the new signature. However, this is a critical call path and the parameter swap could introduce subtle bugs if the compose function's internal logic depends on parameter order in ways not immediately obvious from the signature.

→ Check: Trace through the compose function logic to confirm that errorHandler and notFoundHandler are used correctly in all code paths (lines 32, 42, 66 in compose.ts). Verify that error handling still works as expected in all scenarios.

### 🟢 Low — src/hono.ts:64 — other

The default `notFoundHandler` and `errorHandler` are now module-level constants instead of instance methods. This is a minor refactor that improves memory efficiency but changes the reference identity. The identity check at line 125 relies on this, which could be fragile if the constants are ever redefined or if instances are created in different module contexts.

→ Check: Verify that the module-level constants are truly singleton and won't be redefined. Confirm that the identity check at line 125 works correctly in all module loading scenarios (e.g., bundlers, dynamic imports).
