## Summary
This PR adds fallback handling for environments where `Response.clone()` is not supported (e.g., AWS Lambda). When cloning fails, it reads the response as an ArrayBuffer and reconstructs the Response. The `generateDigest` function is updated to accept both ReadableStream and ArrayBuffer inputs.

## Findings (4)

### 🟡 Medium — src/middleware/etag/index.ts:101 — data-loss

After calling `res.arrayBuffer()` on line 101, the response body is consumed and cannot be read again. The original response body is lost before being sent to the client. On line 103, a new Response is created from the buffer and assigned to `c.res`, but this happens inside the catch block only. If the response was already partially sent or if there are other middleware that depend on the original response, this could cause issues.

→ Check: Verify that in the fallback path, the reconstructed Response on line 103 properly preserves all response properties (status, statusText, headers) and that the body is correctly available for downstream consumers. Test that the response body is not lost when sent to the client.

### 🟡 Medium — src/middleware/etag/index.ts:103 — api-contract

The fallback creates a new Response object from the buffer, but the second argument `res` is passed as the init object. This relies on Response constructor accepting a Response object as init, which may not be standard behavior. The constructor typically expects a ResponseInit object with specific properties. This could fail or behave unexpectedly in some environments.

→ Check: Verify that `new Response(buffer, res)` correctly copies all necessary properties (status, statusText, headers) from the original response. Consider explicitly constructing the init object: `new Response(buffer, { status: res.status, statusText: res.statusText, headers: res.headers })`.

### 🟢 Low — src/middleware/etag/digest.ts:20 — unhandled-edge-case

The check `if (input instanceof ArrayBuffer)` will not catch all ArrayBuffer-like objects (e.g., SharedArrayBuffer). While this is unlikely to be an issue in practice, it's worth noting that the type signature accepts `ArrayBuffer` but the runtime check is specific.

→ Check: Confirm that SharedArrayBuffer or other ArrayBuffer-like types are not expected inputs, or add appropriate handling if they are.

The test only checks that the ETag is generated and the status is 200, but doesn't confirm the body content is intact after the fallback path reconstructs the Response.
