## Summary
This PR makes app.route() propagate a mounted sub-app's custom errorHandler by wrapping its route handlers via compose(), and reorders compose()'s parameters (onError before onNotFound), with tests added for both onError and notFound scenarios. The main risk is the breaking change to compose()'s parameter order since it's exported and could affect external callers with a different signature order, plus a behavioral asymmetry where onError propagates from mounted sub-apps but notFoundHandler does not, which may confuse users expecting symmetric behavior.

## Findings (3)

### 🟡 Medium — src/hono.ts:122 — api-contract

The compose() function argument order was swapped (onError before onNotFound). This is a breaking change for any external code (or middleware packages) directly calling compose() with the old (middleware, onNotFound, onError) signature. Since compose is exported, third-party consumers who imported it directly would silently get wrong behavior (their notFound handler treated as errorHandler and vice versa) without a type error catch in JS usage, only caught by TS type mismatch in strict typed code.

→ Check: Check if compose is part of the public API/exports and search for external usages or documentation referencing compose's parameter order; consider a major version bump or keeping backward-compatible named options.

### 🟡 Medium — src/hono.ts:130 — unhandled-edge-case

In route(), sub-app's notFoundHandler is not wrapped/composed the way errorHandler is — only errorHandler is applied via compose when it differs from default. This means when a sub app defines a custom notFound handler but the route is matched (not a 404), that's fine, but the new test 'notFound' shows sub's custom notFound handler is bypassed and app's notFound is always used for mounted routes, which may not match the intended feature (test expectcs app's handler always wins for implicit 404 in sub-mounted paths) — this looks intentional per tests but is a behavioral asymmetry between error and notFound handling that could confuse users who expect symmetric behavior between onError and notFound when mounted via app.route().

→ Check: Verify product intent: should sub.notFound() only apply for its own standalone app.request() calls and never for mounted sub-apps, while sub.onError() applies even when mounted? Confirm this asymmetry is documented so users aren't surprised that only errorHandler carries over on mount but notFoundHandler doesn't.

### 🟢 Low — src/hono.ts:125 — performance

When a sub-app has a custom errorHandler, every route handler from that sub-app gets wrapped via compose([r.handler], app.errorHandler) at route-mount time, adding an extra layer of function composition/overhead per request for mounted sub-apps with custom error handling. This is likely negligible but worth confirming performance impact for apps with many nested sub-routes.

→ Check: Benchmark route composition overhead for apps with many sub-routes that define custom onError handlers.
