## Summary
This PR adds a fallback in the etag middleware for environments (e.g., AWS Lambda) where res.clone() throws, by buffering the response body via arrayBuffer() and recomputing the digest, then rebuilding c.res. The change is a targeted, additive fix with a test, but the broad try/catch could mask unrelated errors, and the fallback fully buffers the body in memory, which are worth a quick manual sanity check but not blocking.

## Findings (4)

### 🟡 Medium — src/middleware/etag/index.ts — unhandled-edge-case

In the fallback path, res.arrayBuffer() consumes the body of the original response object 'res', but 'res' is later replaced with 'new Response(buffer, res)' assigned to c.res. However, if any other code path downstream (or other middleware finalizing the response after this middleware) still references the original 'res' object (not c.res) expecting an unconsumed body, it would now be empty. Since this middleware presumably runs post-handler via c.res reassignment, this is likely fine, but the pattern of catching only the res.clone() failure while assuming .arrayBuffer() will succeed is fragile — if res.body is a ReadableStream that has already been partially read elsewhere, arrayBuffer() could throw or produce truncated data silently.

→ Check: Verify that no other middleware or code holds a reference to the pre-etag 'res' expecting its body to still be readable after this fallback runs, and confirm res.arrayBuffer() cannot throw or hang in target runtimes (e.g., Lambda) given large bodies or streaming responses.

### 🟡 Medium — src/middleware/etag/index.ts — error-handling

The catch block catches ANY error thrown by res.clone() (or by generateDigest on the cloned body) and treats it as a 'clone not supported' scenario, then re-reads the body via arrayBuffer(). If the original error was something else (e.g., a transient error in the digest generator itself, unrelated to cloning), the fallback logic would silently mask it and potentially produce incorrect or duplicated body consumption behavior, since it doesn't narrow the catch to specifically clone() failures.

→ Check: Confirm the catch block only wraps the res.clone() call (not the full generateDigest call) so unrelated errors from the digest generator aren't silently swallowed and misattributed to a clone failure.

### 🟢 Low — src/middleware/etag/index.ts — performance

In the fallback path, response body is buffered entirely into memory via arrayBuffer() rather than streamed, which could be a performance/memory concern for large response bodies in Lambda-like environments, though this is arguably unavoidable given the constraint.

→ Check: Confirm expected response sizes in Lambda deployments are small enough that buffering the whole body in memory is acceptable.

### 🟢 Low — src/middleware/etag/digest.ts — api-contract

generateDigest's exported input type signature was widened to accept ArrayBuffer in addition to ReadableStream<Uint8Array> | null; other internal or external callers of this function (if any exist beyond etag/index.ts) should be checked to ensure they still work correctly with the new type, though this is an additive change and likely backward compatible.

→ Check: Search codebase for other importers of generateDigest to confirm no assumptions are broken by the widened parameter type.
