## Summary
This PR reorders compose()'s parameters (onError before onNotFound) and adds logic so that when a sub-app is merged into a parent via app.route(), the sub-app's custom errorHandler (but not its custom notFoundHandler) is preserved by wrapping the route handler in a compose call. New tests validate the errorHandler propagation and confirm notFound handling still falls back to the parent's handler, which is expected per the PR's stated scope (errorHandler only, follow-up to notFoundHandler support presumably in #866). The main risk is the parameter reordering in the public compose() function, which is a breaking change for any direct external callers, plus the asymmetry between onError and notFound merge behavior which could surprise users.

## Findings (4)

### 🟡 Medium — src/hono.ts — api-contract

compose()'s parameter order was swapped (onError before onNotFound). This is a breaking change to the exported compose function's signature. Any external consumer (middleware libraries, tests, or downstream code) calling compose(middleware, onNotFound, onError) positionally will now silently pass onNotFound as onError and vice versa, causing wrong handler to be invoked with no type error since both are optional parameters of different but structurally similar function types (though TS would catch obvious type mismatches, if both omitted or one omitted it may not fail).

→ Check: Confirm compose is not part of the public API used by third-party middleware; if it is exported/documented, add a migration note or keep backward-compatible overload ordering.

### 🟡 Medium — src/hono.ts — unhandled-edge-case

In route(), sub-app handlers are now wrapped with compose([r.handler], app.errorHandler) only when app.errorHandler !== default errorHandler. However, this wrapping does not pass the sub-app's notFoundHandler, so a custom notFound handler set on a mounted sub-app will not be used when merged into the parent (confirmed by the added test '/sub/implicit-404 should be handled by app', which shows sub's custom notFound handler is NOT preserved on merge — only errorHandler is wired, notFoundHandler falls back to parent). This is somewhat expected by design (title says errorHandler only) but could confuse users expecting consistent behavour between onError and notFound customization on sub-apps.

→ Check: Verify documentation clarifies that sub.notFound() is not honored when using app.route(), only sub.onError() is, to avoid confusing bug reports.

### 🟢 Low — src/hono.ts — performance

Wrapping each merged route handler in a new compose(...) closure when a custom errorHandler is present adds an extra function call/closure per request compared to directly calling r.handler; negligible but worth noting for very hot routes.

→ Check: No action needed unless profiling shows overhead in high-throughput scenarios.
