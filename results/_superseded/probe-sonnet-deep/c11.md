## Summary
This PR extends greedy/regex-capturing route segments (e.g. `:dirs{.+}`) to also respect a subsequent static path segment, across LinearRouter, TrieRouter and RegExpRouter's shared `getPattern` util, plus new trie-router logic that requeues nodes by consumed path-component count. The biggest risk is that the "next" static segment is interpolated unescaped into a `new RegExp(...)` lookahead (`(?=${next})` in linear-router, `(?=/${next})` in url.ts) — any regex metacharacter in that literal path segment (very plausible, e.g. `.` in `file.html`, or `(`, `)`, `[`, `]` in odd but valid path segments) is treated as a regex operator rather than a literal, which can silently produce false-positive/overly-permissive matches or throw a RegExp syntax error at match time (linear-router builds this regex per-request inside `match()`), potentially surfacing an uncaught exception per request for a previously-fine route.

## Findings (3)

### 🟡 Medium — src/router/linear-router/router.ts:90 — unhandled-edge-case

`next` (the raw next static path segment) is interpolated directly into `new RegExp(pattern + lookahead)` without escaping regex metacharacters. Since this runs inside `match()` on every request for routes using `:label{pattern}` followed by a static segment, a next segment containing chars like `.`, `(`, `)`, `[`, `]`, `+`, `*` (all valid in URL path segments, e.g. `file.html`) will either be treated as regex operators (silently loosening the match, e.g. `.` matches any char instead of literal dot) or, for unbalanced constructs, throw a RegExp syntax error uncaught by the router, turning what should be a 404 into an unhandled exception.

→ Check: Verify whether `next` should be escaped (e.g. via a regex-escape helper) before being embedded in the lookahead, and add a test with a next segment containing `.` or `(` to confirm behavior is intentional, not accidental.

### 🟡 Medium — src/utils/url.ts:64 — unhandled-edge-case

Same unescaped interpolation issue: `getPattern` builds `new RegExp(`^${match[2]}(?=/${next})`)` where `next` is a literal path segment (e.g. from `splitRoutingPath`). This function backs both RegExpRouter and TrieRouter, so the same false-positive-match / possible-throw risk applies broadly; the new tests only exercise a benign literal ('next') and don't cover metacharacter-containing static segments.

→ Check: Add a test where the static segment following a capturing group contains regex metacharacters (e.g. `/:dirs{.+}/foo.bar`) and confirm matching behaves as intended (literal match) rather than being interpreted as regex.

### 🟢 Low — src/router/trie-router/node.ts:180 — unhandled-edge-case

The new `curNodesQueue` requeuing logic derives `componentCount` by counting `/` occurrences in the greedy match (`m[0].match(/\//)?.length ?? 0`) to decide which future loop iteration should pick up the child node. This assumes the matched substring's slash count exactly corresponds to how many `parts` entries it consumed after rejoining with `/`, which should generally hold given `restPathString = parts.slice(i).join('/')`, but is a non-obvious invariant; if the regex pattern were to match a partial/trailing overlapping substring not aligned to component boundaries, indexing into `curNodesQueue` could be subtly wrong (e.g., matching fewer or more slashes than actual consumed parts).

→ Check: Trace through a route with `:x{.+}` followed by two static segments and confirm nodes are queued/matched at exactly the right iteration; consider a test with an empty path segment (double slash) in the captured group.
