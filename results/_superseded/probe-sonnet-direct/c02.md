## Summary
This PR adds a try/catch fallback around res.clone() in the etag middleware for environments (e.g., possibly Lambda) where clone() isn't supported, buffering the response instead of streaming it, and updates generateDigest to accept an ArrayBuffer input. The main risk is that the catch block is overly broad — it will swallow any error from generateDigest or clone(), not just clone-unsupported errors, potentially masking unrelated bugs and changing behavior unexpectedly. Overall this is a narrowly scoped, low-risk bugfix with a reasonable test added, but the broad catch and its behavior difference (buffering vs streaming) merit a quick manual check.

## Findings (3)

### 🟡 Medium — src/middleware/etag/index.ts — unhandled-edge-case

The fallback catch block catches ALL errors thrown from res.clone().body or generateDigest, not just clone-not-supported errors. If generator(hash function) throws for another reason (e.g. crypto failure), it will silently retry via arrayBuffer() path, masking the real error and potentially double-consuming/duplicating body reads. This conflates 'clone unsupported' with any other exception.

→ Check: Verify only clone() failures are caught (e.g., wrap only the res.clone() call in try/catch, not the whole generateDigest call), or check for a specific error type/environment before falling back.

### 🟢 Low — src/middleware/etag/index.ts — performance

In the fallback path, the response body is fully buffered via arrayBuffer() instead of streamed, which changes behavior for large responses (memory usage) compared to the streaming path taken in the normal case. This differs from previous streaming behavior only in the fallback, which is probably intended but worth confirming for large payloads in serverless environments with memory limits.

→ Check: Confirm memory limits (e.g., Lambda's default 128MB-3GB) are acceptable for buffering full response bodies before etag computation, and document the behavior difference.

### 🟢 Low — src/middleware/etag/index.ts — api-contract

c.res is reassigned to `new Response(buffer, res)` in the fallback, which copies status/headers from the original res but not verified to match all header behaviors (e.g., duplicated content-length recalculation, streaming headers). This could silently alter headers/behavior in edge cases not covered by the added test.

→ Check: Add a test verifying headers (e.g., Content-Length, Content-Type) are preserved correctly when the fallback path is triggered, not just ETag and body text.
