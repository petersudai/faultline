_"feat(router): support greedy matches with subsequent static components."_

## Summary
This PR extends greedy/capturing route segments (e.g. `:dirs{.+}`) to support lookahead against a following static path component across the linear and trie routers, with corresponding tests, while RegExpRouter explicitly does not support the new cases (added to an exclusion list). The main risks are: raw string interpolation of the "next" static segment into regex lookaheads without escaping special characters (potential subtle mismatches for segments with dots/other regex metachars), and structural changes in trie-router's Node (mutable shared `#params` state, key computation based on pattern including lookahead) that merit careful review for correctness under multiple concurrent/varied routes. Given three router backends now diverge in supported behavior for the same route syntax, and there's an unescaped-regex-injection-like edge case, this needs some human validation before merging but is not fundamentally destabilizing.

## Findings (5)

### 🔴 High — src/utils/url.ts — unhandled-edge-case

The lookahead regex is built as new RegExp(`^${match[2]}(?=/${next})`) using the raw `next` string directly interpolated into a regex. If `next` contains regex special characters (e.g. '.', '(', ')', '+', etc., which are common in static path segments like 'file.html' as seen in the added tests), they will be interpreted as regex metacharacters rather than literal characters. This can cause false positive or false negative matches for static path segments containing dots or other special chars (a very common case, e.g. '.html', '.json' extensions). The PR's own test uses 'file.html' which contains a '.', and by luck '.' as regex matches any char so it still matches, but it silently changes matching semantics (e.g., 'fileXhtml' would also match) — a subtle correctness bug for any route with special characters in the trailing static segment.

→ Check: Verify behavior with static next segments containing regex metacharacters (e.g. '.', '+', '(', ')', '[', ']') — confirm they are escaped before being embedded in the lookahead regex, and add a test asserting that a literal '.' does not match arbitrary characters.

### 🟡 Medium — src/router/trie-router/node.ts — unhandled-edge-case

The insert() method now computes `key` as `pattern[0]` when pattern is an array, which for a regex pattern with lookahead now embeds the `next` segment into the label/cache key (e.g. ':id{[0-9]+}#next'). This means the same route pattern with different subsequent static segments will create different child node keys in the trie, potentially causing node duplication or divergent matching behavior compared to the previous simpler indexing by `p`. This interacts with the shared `patternCache` mutated by key across multiple route additions and could produce unexpected behavior if two different routes share the same dynamic segment string but differ only in the following static segment, especially combined with `child.#params = params` mutation shared across multiple matched nodes in match(), which could leak params between different route matches if the same child node object is reused for different capture values.

→ Check: Add trie-router-specific tests with multiple sibling routes sharing the same capturing segment but different following static/dynamic segments, and verify no param leakage across concurrent/interleaved matches (especially since `child.#params = params` mutates node state which could be an issue with concurrent execution or reused matcher instances).

### 🟡 Medium — src/router/trie-router/node.ts — concurrency

The change introduces `child.#params = params` as an assignment on the Node object itself (shared, mutable state) when a regex capture has children. Since Node instances are shared across multiple match() calls (the router is built once and reused for all incoming requests), concurrently handling requests that traverse the same regex-capturing node could overwrite `#params` from one request with another's params before it is read, since JS is single-threaded per call but if match() is re-entrant/async in some usage, or if the queue processing across `curNodesQueue` array indexes doesn't fully isolate per-request state, this could cause params from one match to leak into another. This deserves careful review since it's a structural change from purely local computation to mutating shared node state.

→ Check: Trace whether `#params` assigned on the Node during match() could be read by a subsequent, unrelated match() call before being overwritten, particularly under concurrent request handling in the same router instance.

### 🟢 Low — src/router/linear-router/router.ts — unhandled-edge-case

Similar to url.ts, the linear router builds `(?=${next})` directly from the raw next path segment without escaping regex metacharacters, which could produce incorrect matches for static segments containing special characters like '.', '+', '(' etc.

→ Check: Add a test with a following static segment containing a regex special character (not just '.') to confirm correct literal matching, e.g. a segment like 'v1.2(beta)'.

### 🟢 Low — src/router/reg-exp-router/router.test.ts — test-gap

Two new test cases are added to a skip/exclusion list rather than being made to pass for RegExpRouter, indicating this router does not support the new greedy-match-with-static-suffix feature, creating inconsistent behavior across the three router implementations (linear, trie, regexp) for the same route patterns.

→ Check: Confirm this is intentional and documented as a known limitation of RegExpRouter, and that users relying on RegExpRouter (a commonly recommended router for production) are not silently given different matching behavior than trie/linear routers for the same routes.
