## Summary
This PR adds support for greedy regex patterns with subsequent static components in routes (e.g., `/:dirs{.+}/file.html`). The main changes are: (1) `getPattern()` now accepts a `next` parameter to add lookahead assertions to regex patterns when followed by static components, (2) trie-router's search method now uses `exec()` instead of `test()` to capture matched text and queues nodes for deferred processing, and (3) linear-router adds similar lookahead logic. The implementation includes comprehensive tests. However, there are critical regex injection vulnerabilities where unescaped route components are interpolated into regex patterns, and a cache key inconsistency that could cause routing conflicts.

## Findings (4)

### 🔴 High — src/utils/url.ts:65 — security

The `next` parameter is directly interpolated into a regex pattern without escaping: `new RegExp(`^${match[2]}(?=/${next})`)`. If `next` contains regex metacharacters (e.g., '.', '*', '+', '(', ')'), it will be interpreted as regex syntax rather than a literal string, causing unintended pattern matching. Route components like `/:id{.+}/file.test.js` would have `.test.js` interpreted as regex, matching any character before `js`.

→ Check: Escape the `next` parameter using a regex escaping function before interpolating it into the regex pattern.

### 🔴 High — src/router/linear-router/router.ts:90 — security

The `next` variable is interpolated into a lookahead regex without escaping: `const lookahead = next && next[1] !== ':' && next[1] !== '*' ? `(?=${next})` : ''`. The `next` value (which is `parts[j + 1]`) could contain regex metacharacters, leading to unintended pattern matching.

→ Check: Escape `next` before using it in the regex lookahead.

### 🟡 Medium — src/utils/url.ts:67 — api-contract

The pattern array's first element is inconsistent: when a lookahead is added, it returns `cacheKey` (e.g., ':id{[0-9]+}#next'), but without lookahead it returns `label` (e.g., ':id{[0-9]+}'). This inconsistency is used as a trie node key in node.ts line 50. While this works for the tested scenarios, it could cause issues if the same greedy pattern appears in multiple route contexts with different subsequent components, potentially creating duplicate or conflicting trie branches.

→ Check: Verify that routes with the same greedy pattern but different subsequent static components (e.g., '/:id{.+}/a' and '/:id{.+}/b') route correctly and don't create conflicting trie entries.

### 🟢 Low — src/router/reg-exp-router/router.test.ts:14 — test-gap

This suggests the RegExpRouter may not support the new greedy pattern feature, but there's no comment explaining why or whether this is intentional. This could indicate incomplete feature coverage.

→ Check: Clarify whether RegExpRouter is intentionally excluded from supporting greedy patterns with subsequent static components, and add a comment explaining the reason if so.
