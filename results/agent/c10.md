## Summary
This PR adds support for custom hashing methods to the etag middleware by introducing a `generateDigest` option that allows users to specify their own digest generation function (e.g., SHA-256 instead of the default SHA-1). The implementation is backward-compatible with a sensible default. However, there are concerns about error handling for custom generators and the removal of explicit body consumption before 304 responses.

## Findings (2)

### 🟡 Medium — src/middleware/etag/index.ts:79 — error-handling

The `await generateDigest(res.clone().body, generator)` call is not wrapped in try-catch. If the custom `generator` function rejects or throws, the promise rejection will propagate uncaught, potentially crashing the middleware or leaving the response in an inconsistent state. The function returns early on null but doesn't handle promise rejections from the generator.

→ Check: Wrap the `await generateDigest(res.clone().body, generator)` call in a try-catch block to gracefully handle generator failures. Define fallback behavior (e.g., skip ETag generation, use default algorithm, or return error response).

### 🟡 Medium — src/middleware/etag/index.ts:87 — unhandled-edge-case

The removal of `await c.res.blob()` (previously at line 74 in base version) before creating the 304 response changes the resource cleanup behavior. While the cloned body used for digest generation is consumed, the original response body stream may not be explicitly consumed before being discarded. This could potentially leave resources unconsumed in certain edge cases, though the existing tests pass.

→ Check: Verify that removing `await c.res.blob()` doesn't cause resource leaks or improper stream cleanup in production scenarios, especially with large response bodies or streaming responses. Consider adding a test that explicitly verifies the original response body is properly handled when a 304 response is generated.
