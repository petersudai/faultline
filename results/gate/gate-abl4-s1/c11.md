## Summary
This PR adds support for greedy regex patterns followed by static route components (e.g., `/:dirs{.+}/file.html`) by using positive lookahead assertions and a queue-based node deferral system. The implementation is well-tested for simple cases, but there is a critical bug in the trie-router's queue indexing logic that would cause routes to fail when a greedy match consumes multiple path segments.

## Findings (3)

### 🔴 High — src/router/trie-router/node.ts:206 — unhandled-edge-case

The queue deferral logic uses `curNodesQueue.shift()` unconditionally every iteration, but nodes are stored at index `componentCount` (the number of slashes consumed by the greedy match). When a greedy match consumes N slashes (componentCount=N), the child node is stored at curNodesQueue[N], but shift() removes from index 0. This causes nodes stored at indices > 0 to never be processed. For example, with path `/foo/bar/file.html` matching `/:dirs{.+}/file.html`, the greedy match consumes `foo/bar` (1 slash), storing the node at curNodesQueue[1], but the next iteration shifts from index 0, leaving the node unprocessed. This would break routes with greedy matches consuming multiple segments that have child routes.

→ Check: Add a test case with a route like `/:prefix{.+}/middle/suffix/extra` and verify it matches paths like `/a/b/middle/suffix/extra` correctly. The current tests only cover cases where greedy matches consume 0-1 segments or don't have child routes to process.

### 🟡 Medium — src/utils/url.ts:62 — api-contract

The `getPattern()` function signature changed from `getPattern(label: string)` to `getPattern(label: string, next?: string)`. The cache key now includes the `next` parameter (`${label}#${next}`), which means the same pattern with different next components will be cached separately. This is correct for functionality but changes the cache behavior. Callers must pass the `next` parameter consistently, or patterns may be cached incorrectly. The trie-router correctly passes `nextP`, but any other callers (if they exist) must be updated.

→ Check: Search the codebase for all calls to `getPattern()` to ensure they all pass the `next` parameter when appropriate. Verify that the linear-router and any other routers handle the signature change correctly.

### 🟡 Medium — src/router/linear-router/router.ts:89 — error-handling

The lookahead logic checks `next && next[1] !== ':' && next[1] !== '*'` to determine if a lookahead is needed. However, this assumes `next` is a non-empty string. If `next` is an empty string (which shouldn't happen but could due to edge cases in path parsing), accessing `next[1]` would return `undefined`, and the condition would be false, potentially missing the lookahead. Additionally, the logic doesn't account for optional parameters (`:id?`), which start with `:` but should still trigger lookahead in some cases.

→ Check: Verify that `parts[j + 1]` is never an empty string in the linear-router. Add defensive checks or clarify the invariant. Test with optional parameters like `/:prefix{.+}/middle/:id?` to ensure lookahead works correctly.
