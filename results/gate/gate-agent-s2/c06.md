## Summary
This PR reorders parameters in the `compose` function (swapping `onNotFound` and `onError`), extracts default handlers as module-level constants, and implements a feature to use a sub-app's custom errorHandler when composing routes. While all call sites are updated and tests added, the parameter reordering is a breaking API change that could silently break external callers passing positional arguments.

## Findings (3)

### 🔴 High — src/compose.ts:12 — breaking-change

The `compose` function signature changes parameter order from `(middleware, onNotFound?, onError?)` to `(middleware, onError?, onNotFound?)`. This is a breaking change for any external code calling `compose` with positional arguments. Code like `compose(handlers, notFoundFn, errorFn)` will now pass `notFoundFn` to the `onError` parameter and `errorFn` to the `onNotFound` parameter, silently inverting behavior. The PR updates internal call sites but cannot control external usage.

→ Check: Verify whether `compose` is part of the public API or only used internally. If public, this requires a major version bump and migration guide. If internal-only, confirm all external consumers (if any) have been identified and updated.

### 🟡 Medium — src/hono.ts:124 — unhandled-edge-case

The route composition logic checks `app.errorHandler === errorHandler` to decide whether to wrap the handler with `compose`. This identity check is fragile: if a sub-app's errorHandler is reassigned to a new function with identical behavior, or if the reference is lost, the check fails silently. Additionally, the logic only wraps with `app.errorHandler` but does not wrap with `app.notFoundHandler`, creating asymmetry. The test coverage does not verify what happens if a sub-app has a custom notFoundHandler.

→ Check: Confirm the intent: should sub-app notFoundHandlers also be composed into routes? If yes, add wrapping logic and tests. If no, document why errorHandler is special. Consider a more robust way to track whether handlers are custom (e.g., a flag) rather than identity comparison.

### 🟢 Low — src/hono.ts:66 — other

The extracted `notFoundHandler` and `errorHandler` are module-level constants, not instance-specific. All Hono instances share the same default handler references. While this is likely intentional for memory efficiency, it means the identity check `app.errorHandler === errorHandler` works only if the instance never calls `onError()` to override the handler. This is correct but subtle and worth documenting.

→ Check: Verify that calling `app.onError()` or `app.notFound()` replaces the instance's handler reference (not mutating the shared constant). Confirm tests cover this scenario.
