## Summary
This PR refactors `c.json()` and `c.text()` to use a shared `#useFastPath()` helper that bypasses `#newResponse()` when no customization is present. The optimization is sound in principle, but `Response.json()` has subtly different behavior from the manual path—it may set different headers or handle edge cases differently—and this is not tested.

## Findings (2)

### 🟡 Medium — src/context.ts:711 — api-contract

The fast path uses `Response.json(object)` directly, which is a standard Web API. However, the slow path calls `this.#newResponse(JSON.stringify(object), arg, setDefaultContentType('application/json', headers))`. These two paths may produce observably different responses: `Response.json()` sets its own Content-Type header and may handle serialization, charset, or other headers differently than the manual `JSON.stringify()` + `setDefaultContentType()` flow. Without explicit tests confirming equivalence, callers relying on specific header values or serialization behavior could see a change in output.

→ Check: Write a test that calls `c.json({...})` with no parameters and verify: (1) the Content-Type header matches what the slow path produces, (2) the response body is byte-for-byte identical, (3) any other headers (e.g., charset) are the same. Compare against the slow path output to confirm equivalence.

### 🟢 Low — src/context.ts:681 — test-gap

The refactoring of `c.text()` to use `#useFastPath()` is correct, but the condition changed from `!this.#preparedHeaders && !this.#status && !arg && !headers && !this.finalized` to `this.#useFastPath() && !arg && !headers`. This is logically equivalent, but the extraction into a helper makes the intent clearer. No test explicitly covers the fast path for `c.text()` either.

→ Check: Add a test for `c.text('hello')` with no parameters to confirm the fast path is exercised and produces correct output (status 200, Content-Type: text/plain).
