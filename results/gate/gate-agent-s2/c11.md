## Summary
This PR adds lookahead-based matching for greedy regex patterns followed by static path components. The implementation modifies pattern caching, trie-node traversal, and linear-router matching logic. While test coverage is comprehensive, there are unresolved behavioral changes in pattern matching and a critical test exclusion that masks potential regressions.

## Findings (5)

### 🔴 High — src/router/reg-exp-router/router.test.ts:15 — test-gap

Two test cases from the new 'Capture complex multiple directories' suite are explicitly excluded from RegExpRouter testing. This suggests the RegExpRouter implementation does not support the new lookahead-based matching behavior, creating a divergence between router implementations. The exclusion masks whether this is a known limitation or a regression.

→ Check: Verify whether RegExpRouter is intentionally unsupported for greedy patterns with lookahead, or whether its implementation needs updating. If intentional, document why and ensure callers are aware of the limitation.

### 🔴 High — src/utils/url.ts:62 — api-contract

The `getPattern` function signature changed from `(label: string)` to `(label: string, next?: string)`, and its return value structure changed when `next` is provided (e.g., `[':id{[0-9]+}#next', 'id', /^[0-9]+(?=\/next)$/]` vs `[':id{[0-9]+}', 'id', /^[0-9]+$/]`). The first element of the returned tuple is now sometimes a cache key (with `#next` suffix) rather than the original label. This breaks the contract for any code relying on the first tuple element being the original pattern string.

→ Check: Audit all callers of `getPattern` to confirm they do not depend on the first tuple element being the original label. Check if the cache key format leaking into the return value causes issues in pattern reconstruction or logging.

### 🔴 High — src/router/trie-router/node.ts:49 — unhandled-edge-case

The `key` variable is now derived from `getPattern(p, nextP)`, which can return a cache key like `:id{[0-9]+}#next` instead of the original pattern. This key is used to index `curNode.#children`, but the trie structure was built with the original pattern strings as keys. This mismatch means lookups will fail for patterns with lookahead, and new nodes will be created under incorrect keys, fragmenting the trie.

→ Check: Verify that the trie node children are correctly keyed. Add a test that adds the same pattern twice (once with lookahead context, once without) and confirm they resolve to the same node, not duplicates.

### 🟡 Medium — src/router/trie-router/node.ts:120 — unhandled-edge-case

The new `curNodesQueue` is initialized as an empty array but only populated conditionally inside the regex match block. If a greedy pattern matches but the child node has no further children, the queue remains empty for that iteration. The queue is shifted unconditionally at line 206 (`curNodesQueue.shift() ?? []`), which could cause queue indices to drift if some iterations do not populate their expected slot, leading to nodes being processed at the wrong depth.

→ Check: Trace through a scenario where a greedy pattern matches multiple path segments but intermediate nodes have no children. Confirm that `curNodesQueue` indices align correctly with the number of path segments consumed by the regex match.

### 🟡 Medium — src/router/linear-router/router.ts:89 — unhandled-edge-case

The lookahead is constructed as `(?=${next})` where `next` is `parts[j + 1]`. If `next` contains special regex characters (e.g., `[`, `(`, `.`), they are not escaped, causing the lookahead to be malformed. For example, if the next part is `:id{[0-9]+}`, the lookahead becomes `(?=:id{[0-9]+})`, which is invalid regex syntax.

→ Check: Add a test case with a greedy pattern followed by a part containing regex metacharacters (e.g., `/:dirs{.+}/:id{[0-9]+}`). Verify the pattern compiles and matches correctly.
