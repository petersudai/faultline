## Summary
This PR reorders parameters in the `compose` function (swapping `onNotFound` and `onError`), extracts default handlers as module-level constants, and implements a feature to use a sub-app's custom errorHandler when composing routes. While all call sites are updated and tests added, the parameter reordering is a breaking API change that could silently break external callers.

## Findings (3)

### 🔴 High — src/compose.ts:12 — breaking-change

The `compose` function signature changes the order of optional parameters from `(middleware, onNotFound?, onError?)` to `(middleware, onError?, onNotFound?)`. This is a breaking change for any external code calling `compose` with positional arguments. An external caller passing `compose(handlers, notFoundFn, errorFn)` will now have those handlers swapped with no compile-time error (both are optional and have compatible signatures in many cases). The PR updates internal call sites but cannot control external usage.

→ Check: Verify whether `compose` is part of the public API or only internal. If public, this requires a major version bump and migration guide. If internal-only, document the scope clearly. Check if there are any external packages or examples in documentation that call `compose` directly.

### 🟡 Medium — src/hono.ts:124 — unhandled-edge-case

The route composition logic at line 124 checks `app.errorHandler === errorHandler` to decide whether to wrap the handler with `compose`. This identity check is fragile: it assumes the default errorHandler is always the module-level `errorHandler` constant. However, if a sub-app's errorHandler is reassigned or if there are multiple Hono instances with different error handlers, the identity check may fail or succeed unexpectedly. The logic also only wraps with errorHandler but ignores the sub-app's notFoundHandler entirely, which may be intentional but is not documented.

→ Check: Confirm the intended behavior: should sub-app notFoundHandlers be composed into routes, or only errorHandlers? Add a comment explaining why the identity check is safe. Consider whether a flag or explicit configuration would be clearer than relying on reference equality.

### 🟡 Medium — src/hono.test.ts:1030 — test-gap

The new test at line 1030 ('should be handled by sub') expects the sub-app's errorHandler to catch errors thrown in sub-app routes. However, the test does not verify that errors thrown in the parent app's middleware (like the one at line 941) are still caught by the parent's errorHandler. The test coverage for error propagation between nested apps is incomplete.

→ Check: Add a test case where an error is thrown in the parent app's middleware that wraps a sub-app route, and verify it is caught by the parent's errorHandler, not the sub-app's.
