## Summary
This PR adds fallback handling for environments where `res.clone()` fails (e.g., AWS Lambda), but the fallback path processes the response body differently than the normal path. The fallback converts the entire body to an ArrayBuffer and passes it to the generator once, while the normal path streams chunks and accumulates hashes. This architectural difference will produce different ETag values for identical content, breaking cache validation.

## Findings (4)

### 🔴 High — src/middleware/etag/digest.ts:20 — api-contract

The new ArrayBuffer branch (lines 20-21) calls `generator(new Uint8Array(input))` once with the full buffer. The streaming branch (lines 23-30) calls the generator multiple times, passing accumulated results via `mergeBuffers()`. For hash generators that expect incremental input (the typical pattern for streaming), these produce different outputs. The generator contract is violated by the single-call path.

→ Check: Trace through the default SHA-1 generator (or any custom generator used in tests) with identical input data via both paths. Confirm they produce identical hash outputs. If not, the ArrayBuffer path must accumulate chunks identically to the streaming path.

### 🔴 High — src/middleware/etag/index.ts:101 — breaking-change

When `res.clone()` fails, the fallback calls `generateDigest(buffer, generator)` where `buffer` is an ArrayBuffer. This triggers the new single-call path in digest.ts. For the same response body, the normal path (via streaming) and fallback path (via ArrayBuffer) will produce different ETags. This breaks ETag consistency: the same resource will have different ETags depending on whether clone() succeeds, causing cache misses and validation failures.

→ Check: Create a test that generates an ETag for identical content via both the normal path (clone succeeds) and fallback path (clone fails). Verify the ETag values are identical. If they differ, the fallback must be redesigned to accumulate chunks the same way the streaming path does.

### 🔴 High — src/middleware/etag/index.ts:110 — data-loss

Line 110 reassigns `c.res = new Response(buffer, res)` after the body has been consumed by `res.arrayBuffer()`. The original response body is now exhausted and replaced. If any downstream middleware or code expects to read the original response body after this middleware, it will receive an empty or newly-constructed response. This is a silent behavioral change that could break request/response chains.

→ Check: Verify that no downstream middleware or application code reads `c.res.body` or calls `c.res.text()` / `c.res.json()` after the etag middleware runs. If they do, the body will be empty or incorrect. Consider whether the response reconstruction preserves all necessary properties and whether body consumption is idempotent in the calling context.

### 🟡 Medium — src/middleware/etag/index.test.ts:158 — test-gap

The new test verifies that a response is returned with an ETag when clone() fails, but does not verify that the ETag value is consistent with what the normal path produces. The test does not compare ETags from both paths for identical content, so the hash inconsistency bug would not be caught by this test.

→ Check: Add a test that generates the same response content via both the normal path (clone succeeds) and fallback path (clone fails), then compare the ETag headers. They must be identical.
