## Summary
This PR adds support for custom hashing algorithms to the ETag middleware by allowing users to provide a `generateDigest` function option. The implementation correctly threads the custom generator through the call chain and includes tests for SHA-256. The change is backward-compatible with a sensible default (SHA-1), and the removal of the `await c.res.blob()` call appears to be a safe cleanup since the body is already being consumed by `generateDigest`.

## Findings (2)

### 🟢 Low — src/middleware/etag/index.ts:76 — unhandled-edge-case

The removal of `await c.res.blob()` before the 304 response assumes the body has been fully consumed by `generateDigest`. If `generateDigest` is called with a stream that errors mid-read or if a custom generator doesn't fully consume the stream, the body might not be properly drained, potentially causing resource leaks or unexpected behavior in edge cases.

→ Check: Verify that custom `generateDigest` implementations are expected to fully consume the stream, and consider documenting this requirement. Test with a custom generator that partially consumes or errors on the stream.

### 🟢 Low — src/middleware/etag/index.ts:59 — error-handling

The default `generator` function is defined inline and calls `crypto.subtle.digest` without explicit error handling. If `crypto.subtle` is unavailable at runtime (despite the check in `generateDigest`), the error will propagate. However, this mirrors the original behavior, so it's a pre-existing pattern rather than a new risk.

→ Check: Confirm that the `crypto.subtle` availability check in `generateDigest` is sufficient, or add a try-catch in the middleware to handle potential crypto errors gracefully.
