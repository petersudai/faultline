## Summary
This PR adds support for greedy regex patterns (e.g., `/:dirs{.+}`) followed by static path components (e.g., `/file.html`). It modifies the router's pattern matching logic to use lookahead assertions and adds a queue-based mechanism to handle backtracking when greedy matches consume too much. The main risk is complexity in the matching algorithm and potential edge cases in the lookahead/backtracking logic.

## Findings (6)

### 🟡 Medium — src/router/trie-router/node.ts:120 — unhandled-edge-case

The new `curNodesQueue` mechanism uses `componentCount` (derived from counting `/` in the matched string) as an array index. If a greedy pattern matches zero slashes, `componentCount` is 0, and the queue shift logic may not properly handle all backtracking scenarios. The queue is shifted once per iteration, but multiple greedy patterns at different depths could create ordering issues.

→ Check: Verify that paths with multiple greedy patterns at different nesting levels (e.g., `/:a{.+}/middle/:b{.+}/end`) correctly backtrack and match all handlers in the right order.

### 🟡 Medium — src/utils/url.ts:62 — api-contract

The `getPattern` function signature changed to accept an optional `next` parameter, and the cache key now includes `next` (e.g., `label#next`). This changes the return value's first element from the original label to the cache key when `next` is provided. Callers relying on the first element being the original label string may break.

→ Check: Search all callers of `getPattern` to confirm they don't depend on the first element of the returned tuple being the original label string. Verify that the cache key format (`label#next`) doesn't cause issues if used as a route key elsewhere.

### 🟡 Medium — src/router/trie-router/node.ts:49 — unhandled-edge-case

The `key` used for storing children is now derived from the pattern (first element of the tuple). When a pattern with lookahead is created, the key becomes `label#next` instead of the original label. This could cause duplicate nodes if the same pattern is added with different `next` values, or if the pattern is later queried without the lookahead context.

→ Check: Verify that routes with the same greedy pattern but different subsequent static components (e.g., `/:x{.+}/a` and `/:x{.+}/b`) don't create conflicting or duplicate child nodes in the trie.

### 🟡 Medium — src/router/linear-router/router.ts:89 — unhandled-edge-case

The lookahead assertion is added to the regex pattern only if `next` exists and is not a parameter or wildcard. However, the lookahead uses `next` directly without escaping special regex characters. If `next` contains regex metacharacters (e.g., `.`, `+`, `*`), the lookahead will be malformed.

→ Check: Test routes where the static component after a greedy pattern contains regex special characters (e.g., `/:x{.+}/file.json` or `/:x{.+}/a+b`). Verify the lookahead is correctly escaped.

### 🟢 Low — src/router/reg-exp-router/router.test.ts:14 — test-gap

Two test cases are marked as expected failures in the RegExpRouter tests, suggesting the RegExpRouter doesn't support this feature. This is acceptable if RegExpRouter is a legacy or alternative router, but it's worth confirming that the feature is only intended for LinearRouter and TrieRouter.

→ Check: Confirm whether RegExpRouter is actively used and whether it should eventually support greedy patterns with lookahead, or if it's acceptable to leave it unsupported.

### 🟢 Low — src/router/trie-router/node.ts:172 — other

The code now calls `matcher.exec(restPathString)` instead of `matcher.test(restPathString)`, which is more expensive. For patterns that don't match, this adds overhead. However, the exec result is necessary to extract the matched portion for the queue logic, so this is likely unavoidable.

→ Check: Consider whether the performance impact of calling `exec` instead of `test` on every greedy pattern match is acceptable, especially for high-traffic routes.
