## Summary
This PR adds support for greedy regex matches (e.g., `/:dirs{.+}`) followed by static path components (e.g., `/file.html`). The implementation modifies the router's pattern matching logic to use lookahead assertions and adds a queue-based mechanism to defer matching of child nodes. While the feature is well-tested, there are concerns about the correctness of the lookahead logic in edge cases and potential issues with the deferred node matching queue.

## Findings (5)

### 🟡 Medium — src/utils/url.ts:66 — unhandled-edge-case

The lookahead assertion `(?=/${next})` assumes the next component is always preceded by a `/`. However, if `next` is a parameter like `:id`, the lookahead would be `(?=/:id)`, which would fail to match because the regex is applied to the remaining path string that doesn't include the parameter name syntax. This could cause false negatives when a greedy pattern is followed by a parameter.

→ Check: Test cases like `/:dirs{.+}/:id` to verify that greedy patterns correctly match when followed by parameters, not just static components.

### 🟡 Medium — src/router/trie-router/node.ts:203 — unhandled-edge-case

The `curNodesQueue` is indexed by component count (`componentCount = m[0].match(/\//)?. length ?? 0`), but this assumes a linear progression through path components. If multiple greedy patterns match different numbers of components, or if the queue is accessed out of order, nodes could be processed at the wrong depth, causing incorrect routing or missed matches.

→ Check: Add test cases with multiple overlapping greedy patterns that consume different numbers of path components (e.g., `/:a{.+}/x` and `/:b{.+}/y/z`) to verify correct queue ordering and node processing.

### 🟡 Medium — src/router/trie-router/node.ts:180 — error-handling

When a greedy pattern matches and child nodes are queued, the code sets `child.#params = params` (line 180). However, this mutates the child node's state, which could cause issues if the same child node is reached via different paths or if params are overwritten by subsequent matches. This could lead to incorrect parameter values in the final result.

→ Check: Verify that parameter assignment doesn't cause state pollution by testing routes where the same child node is reachable via multiple greedy patterns with different captured values.

### 🟢 Low — src/router/linear-router/router.ts:89 — unhandled-edge-case

The lookahead logic checks `next[1] !== ':' && next[1] !== '*'`, but `next` is a full path component string. For a component like `:id{[0-9]+}`, `next[1]` would be `i`, not `:`. This check appears to be intended to detect if the next component is a parameter or wildcard, but it's checking the wrong character position.

→ Check: Verify that the lookahead is correctly applied only when the next component is static (not a parameter or wildcard) by testing mixed patterns like `/:dirs{.+}/:id` and `/:dirs{.+}/*`.
