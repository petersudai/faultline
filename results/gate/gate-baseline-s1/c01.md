## Summary
This PR adds a fast-path optimization to `c.json()` matching the existing optimization in `c.text()`, avoiding unnecessary allocations when no status, headers, or finalized state exist. The change uses `Response.json()` for the fast path instead of manually constructing a Response with inline headers.

## Findings (3)

### 🟡 Medium — src/context.ts:712 — api-contract

The fast path uses `Response.json(object)` which has different behavior than the slow path `this.#newResponse(JSON.stringify(object), ...)`. Response.json() automatically sets Content-Type and may handle serialization differently. The PR description mentions using 'inline header object' but the code uses Response.json() which creates a Headers instance, not a plain object. This contradicts the stated optimization goal and may not achieve the claimed performance benefits in the node-server adapter.

→ Check: Verify that Response.json(object) produces identical output to JSON.stringify(object) with Content-Type header, and confirm it doesn't create a Headers instance that would negate the node-server adapter optimization mentioned in the PR description.

### 🟡 Medium — src/context.ts:660 — test-gap

The new #useFastPath() helper method is extracted but the fast-path conditions for json() differ from text() — json() adds `!arg && !headers` checks while text() had the same. However, the extraction of #useFastPath() without these conditions means the helper is incomplete. The json() method correctly adds the extra checks, but this pattern could be error-prone if other methods reuse #useFastPath() without understanding the additional constraints needed.

→ Check: Confirm that all callers of #useFastPath() apply the necessary additional condition checks (!arg && !headers) and that no future refactoring accidentally reuses #useFastPath() without these guards.

### 🟢 Low — src/context.ts:678 — other

The text() method was refactored to use the new #useFastPath() helper, changing from an inline condition to a method call. While functionally equivalent, this adds a method call overhead in the hot path. For a performance-focused PR, this micro-optimization trade-off should be intentional.

→ Check: Verify that the method call to #useFastPath() doesn't measurably impact the text() fast path performance, or consider inlining the condition for text() if benchmarks show regression.
