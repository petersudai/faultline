## Summary
This PR adds a fast-path optimization to `c.json()` that mirrors the existing optimization in `c.text()`, avoiding unnecessary allocations when no status, headers, or finalized state exist. The change is low-risk: it's a straightforward performance optimization with no API contract changes, and the fast-path conditions are identical to the proven `c.text()` pattern.

## Findings (2)

### 🟢 Low — src/context.ts:710 — api-contract

The PR switches from `this.#newResponse(JSON.stringify(object), ...)` to `Response.json(object)` in the fast path. While `Response.json()` is a standard Web API that should produce identical output, there's a subtle difference: `Response.json()` internally calls `JSON.stringify()` and sets the Content-Type header. The PR assumes this produces byte-for-byte identical output to the slow path. If there are any edge cases in how `Response.json()` serializes or encodes the JSON (e.g., charset handling, number precision), the fast path could diverge from the slow path behavior.

→ Check: Verify that `Response.json(object)` produces identical serialization and headers to `JSON.stringify(object)` followed by `this.#newResponse()` with `setDefaultContentType('application/json', headers)`. Test with edge cases: large numbers, special characters, Unicode, circular references (if applicable), and verify the exact Content-Type header value (e.g., charset parameter).

### 🟢 Low — src/context.ts:660 — test-gap

The new `#useFastPath()` helper method is extracted and reused in both `text()` and `json()`, but there's no explicit test coverage shown for the fast-path conditions in `json()`. The fast path is only taken when `!arg && !headers` in addition to the base conditions. If a test suite doesn't cover the case where `c.json(obj)` is called with no second or third argument, the fast path may not be exercised.

Verify the output is identical across all cases.
