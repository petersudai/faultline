## Summary
This PR adds support for greedy route parameters followed by static path components by introducing positive lookahead assertions and a queue mechanism. A critical queue indexing bug in the trie-router and unexplained test exclusions in reg-exp-router create high risk of routing failures.

## Findings (3)

### 🔴 High — src/router/trie-router/node.ts:203 — unhandled-edge-case

The queue mechanism stores nodes at `curNodesQueue[componentCount]` (where componentCount is the number of slashes in the greedy match), but unconditionally calls `curNodesQueue.shift()` every iteration. For a greedy match consuming N segments (N-1 slashes), the node is queued at index N-1, but shift() removes from index 0. This causes nodes queued at indices > 0 to be lost or retrieved at the wrong iteration. Example: `/:dirs{.+}/file.html` matching `/foo/bar/file.html` queues the child at index 1, but shift() on iteration 2 removes nothing, leaving the child node orphaned.

→ Check: Trace execution with `/foo/bar/file.html` against `/:dirs{.+}/file.html`. Verify the child node is added back to curNodes at the correct iteration. Consider whether the queue should be a FIFO queue indexed by iteration count rather than by component count, or if the shift should be replaced with indexed access matching the iteration number.

### 🔴 High — src/router/reg-exp-router/router.test.ts:14 — test-gap

Two test cases from the common test suite are explicitly excluded from reg-exp-router: 'Capture complex multiple directories > GET /part1/middle-b/latest' and 'GET /part1/middle-b/end-c/latest'. This indicates the new lookahead-based pattern logic does not work with the reg-exp-router implementation. No explanation, comment, or issue reference is provided. These are concrete test failures that block the feature from working across all router implementations.

→ Check: Run the excluded tests against reg-exp-router and confirm they fail. Either fix the reg-exp-router to support the new lookahead syntax, or add an inline comment explaining why the feature is intentionally unsupported in that router and document the limitation.

### 🟡 Medium — src/utils/url.ts:62 — api-contract

The `getPattern()` function now requires a `next` parameter to generate correct lookahead patterns. The cache key includes `next` (`${label}#${next}`), so the same pattern with different next components produces different cached regexes. If a caller omits the `next` parameter, it will use a cache entry without lookahead, silently degrading behavior. The linear-router correctly passes `nextP`, but any future caller that forgets to pass `next` will not get the lookahead optimization without error.

→ Check: Verify all call sites of `getPattern()` in trie-router and linear-router pass the next component. Consider adding a JSDoc comment or assertion to make the `next` parameter semantically required for patterns with braces, or refactor to make the lookahead logic internal to avoid caller error.
