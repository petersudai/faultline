## Summary
This PR refactors the `env` helper's TypeScript type signature to support flexible generic inference patterns, with expanded test coverage. However, the conditional type in the function signature introduces a subtle contract change that could affect type inference in edge cases, and the runtime behavior change (parameter type narrowing) is not validated.

## Findings (3)

### 🟡 Medium — src/helper/adapter/index.ts:16 — api-contract

The parameter type changed from `c: C` to `c: T extends Record<string, unknown> ? Context : C`. This conditional type means when `T` is provided explicitly, the function now accepts a bare `Context` instead of the full `C` type. This alters the contract: callers passing a context with specific Bindings or Env types may now lose type information. The old signature enforced that `C` must be compatible with the Bindings; the new one does not when `T` is explicit.

→ Check: Verify that existing call sites passing `env<SomeType>(context)` still receive correct type inference for `context.env` and that no type narrowing breaks downstream usage. Test a case where the context has pre-existing Bindings that differ from the explicit generic.

### 🟡 Medium — src/helper/adapter/index.ts:12 — test-gap

The tests verify that type inference works in three scenarios, but they do not test the runtime behavior or edge cases: (1) what happens if `T` and `C['Bindings']` are mismatched, (2) whether the return type `T & C['env']` is correctly computed under the new conditional, (3) whether the function still correctly accesses `c.env` at runtime when the parameter type is narrowed to bare `Context`.

→ Check: Add a test case where `env<T>(c)` is called with a context whose Bindings do not match `T`, and verify the return type and runtime behavior are sensible. Confirm the function still accesses the correct `env` object at runtime.

### 🟢 Low — src/helper/adapter/index.ts:12 — other

The default type for `C` was simplified from `Context<{} & { Bindings: T }>` to `Context<{ Bindings: T }>`. The `{} &` was redundant, so this is a minor cleanup, but it does change the default type signature slightly. This is unlikely to cause issues but is worth noting as a subtle semantic change.

→ Check: Confirm that removing `{} &` does not affect type inference in any existing code that relies on the default `C` type (i.e., when neither `T` nor `C` are explicitly provided).
