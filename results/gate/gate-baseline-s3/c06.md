## Summary
This PR reorders the `compose()` function parameters to prioritize `onError` before `onNotFound`, and implements custom errorHandler propagation when sub-apps are mounted via `app.route()`. The change allows sub-apps to use their own error handlers instead of always falling back to the parent app's handler. The main risk is the parameter reordering is a breaking change to the `compose()` API that could affect external callers.

## Findings (4)

### 🔴 High — src/compose.ts:12 — breaking-change

The `compose()` function signature changes the parameter order from `(middleware, onNotFound?, onError?)` to `(middleware, onError?, onNotFound?)`. This is a breaking change for any external code calling `compose()` directly with positional arguments. While the PR updates internal call sites and tests, external consumers of this exported function will break silently if they pass handlers positionally.

→ Check: Verify that `compose()` is not part of the public API or document this as a breaking change. If it is public, consider using named parameters or a deprecation period. Check if there are any external packages depending on the old signature.

### 🟡 Medium — src/hono.ts:124 — unhandled-edge-case

The logic `app.errorHandler === errorHandler` uses reference equality to detect if a sub-app has a custom error handler. However, if a user explicitly assigns the default `errorHandler` function to their sub-app's errorHandler property, this check will fail and the custom handler won't be wrapped. This is a subtle edge case where the behavior depends on implementation details rather than explicit configuration.

→ Check: Consider adding a flag or property to track whether an errorHandler was explicitly set by the user, rather than relying on reference equality. Alternatively, document this behavior clearly.

### 🟡 Medium — src/hono.ts:123 — missing-caller-update

The `route()` method now wraps handlers with `compose()` when a sub-app has a custom errorHandler, but this wrapping only applies to the route handler itself. If the sub-app has middleware that throws errors, those errors may not be caught by the sub-app's errorHandler in all cases, leading to inconsistent error handling behavior between direct sub-app requests and mounted sub-app requests.

→ Check: Verify that error handling works consistently for all middleware in the sub-app, not just the final route handler. Add tests that throw errors from middleware at different levels.

### 🟢 Low — src/hono.ts:66 — other

The default `errorHandler` and `notFoundHandler` are now module-level constants instead of instance methods. This means all Hono instances share the same function reference for defaults. While this is fine for the default behavior, it could be confusing if someone tries to monkey-patch or override these at the instance level.

→ Check: Ensure documentation clarifies that these are shared defaults and that custom handlers should be set via `onError()` and `notFound()` methods.
