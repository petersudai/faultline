## Summary
This PR adds a fallback mechanism for environments where `Response.clone()` is not supported (e.g., AWS Lambda). When cloning fails, it reads the response body into an ArrayBuffer and regenerates the ETag. The `generateDigest` function is refactored to accept either a ReadableStream or ArrayBuffer.

## Findings (5)

### 🔴 High — src/middleware/etag/index.ts:102 — data-loss

After calling `res.arrayBuffer()`, the response body stream is consumed and cannot be read again. The fallback creates a new Response with the buffer, but the original response body is already exhausted. If the middleware is used in a chain where downstream handlers expect to read the body, they will get an empty stream.

→ Check: Verify that after the fallback path executes, the response body is still readable by downstream middleware and the final consumer. Test with a middleware chain that reads the body multiple times.

### 🟡 Medium — src/middleware/etag/index.ts:101 — error-handling

The catch block catches all errors from `res.clone()`, but `res.clone().body` could also throw if the response object is malformed. The fallback assumes `res.arrayBuffer()` will succeed, but it could also fail. If `res.arrayBuffer()` throws, the error is unhandled and will propagate.

→ Check: Add error handling around the `res.arrayBuffer()` call in the fallback path, or document what errors are expected and how they should be handled.

### 🟡 Medium — src/middleware/etag/index.ts:110 — api-contract

The fallback reassigns `c.res` to a new Response object. This could break downstream middleware or handlers that hold references to the original response object or expect specific properties/methods on it. The new Response may not preserve all properties of the original.

→ Check: Verify that reassigning `c.res` does not break the response pipeline. Check if any middleware after etag() depends on the original response object's identity or properties.

### 🟢 Low — src/middleware/etag/digest.ts:12 — test-gap

The new ArrayBuffer path in `generateDigest` is tested indirectly through the integration test, but there is no direct unit test for the `generateDigest` function with an ArrayBuffer input. The function signature changed to accept a union type, but test coverage for both paths is not explicit.

→ Check: Consider adding a direct unit test for `generateDigest` with an ArrayBuffer input to ensure the logic is correct independent of the middleware integration.

### 🟢 Low — src/middleware/etag/index.test.ts:159 — test-gap

The test mocks `clone()` to throw an error, but it doesn't verify that the fallback path actually executes or that the response body is still readable after the middleware processes it. The test only checks that status, ETag, and text are correct, but doesn't verify the body wasn't consumed twice.

→ Check: Enhance the test to verify that the response body can be read multiple times if needed, or document the limitation that the body is consumed during ETag generation.
