## Summary
This PR adds support for greedy regex patterns with subsequent static components in routes (e.g., `/:dirs{.+}/file.html`). The main changes are: (1) `getPattern()` now accepts a `next` parameter to add lookahead assertions to regex patterns when followed by static components, (2) trie-router's search method now uses `exec()` instead of `test()` to capture matched text and queues nodes for deferred processing, and (3) linear-router adds similar lookahead logic. The implementation includes comprehensive tests. A subtle cache key inconsistency in pattern storage and a potential edge case in component counting warrant verification.

## Findings (2)

### 🟡 Medium — src/utils/url.ts:67 — api-contract

The pattern array's first element is inconsistent: when a lookahead is added, it returns `cacheKey` (e.g., ':id{[0-9]+}#next'), but without lookahead it returns `label` (e.g., ':id{[0-9]+}'). This inconsistency is used as a trie node key in node.ts line 50. While this works for the tested scenarios, it could cause issues if the same greedy pattern appears in multiple route contexts with different subsequent components, potentially creating duplicate or conflicting trie branches.

→ Check: Verify that routes with the same greedy pattern but different subsequent static components (e.g., '/:id{.+}/a' and '/:id{.+}/b') route correctly and don't create conflicting trie entries. Add a test case for this scenario.

### 🟡 Medium — src/router/trie-router/node.ts:180 — unhandled-edge-case

The component count calculation uses `m[0].match(/\//)?.length ?? 0` to count slashes in the matched text. This assumes the matched text contains only forward slashes as path separators. If a parameter value contains encoded slashes or other edge cases, this count could be incorrect, leading to nodes being queued at the wrong depth in curNodesQueue.

→ Check: Test with parameter values that might contain special characters or encoded slashes (e.g., URL-encoded paths). Verify the queue offset calculation is robust.
