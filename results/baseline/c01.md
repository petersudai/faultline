## Summary
This PR adds a fast-path optimization to `c.json()` matching the existing optimization in `c.text()`, avoiding unnecessary allocations when no status, headers, or finalized state exist. The change uses `Response.json()` for the fast path instead of manually constructing a Response with inline headers.

## Findings (3)

### 🟡 Medium — src/context.ts:712 — api-contract

The fast path uses `Response.json(object)` which has different behavior than the slow path `this.#newResponse(JSON.stringify(object), ...)`. Response.json() automatically sets Content-Type and may handle serialization differently. The PR description mentions using 'inline header object' but the code uses Response.json() which creates a Headers instance, not a plain object. This contradicts the stated optimization goal and may not achieve the claimed performance benefits in the node-server adapter.

→ Check: Verify that Response.json(object) produces identical output (including header type and serialization) as JSON.stringify(object) passed through #newResponse(). Confirm whether Response.json() creates a Headers instance or plain object, and whether this aligns with the node-server adapter's optimization expectations.

### 🟡 Medium — src/context.ts:660 — test-gap

The new #useFastPath() helper method is extracted but the fast-path conditions differ between text() and json(): text checks `!arg && !headers` while json() also checks `!arg && !headers`. However, the semantics of 'arg' may differ between text and json responses (text uses it as status/init, json uses it as status/init for the JSON response). No test coverage is visible for the fast path in json() to ensure it handles all edge cases correctly.

→ Check: Add explicit tests for c.json() fast path covering: (1) simple object with no args, (2) with status code, (3) with headers, (4) with both, (5) after finalization, (6) after preparedHeaders set. Verify output matches slow path exactly.

### 🟢 Low — src/context.ts:660 — other

The #useFastPath() helper is now used by both text() and json(), but the conditions are identical. If future changes add different conditions for json vs text, this shared helper could become a source of subtle bugs. The current implementation is safe but slightly fragile.

→ Check: Consider whether #useFastPath() should remain shared or be split into method-specific helpers if the optimization strategies diverge in the future.
