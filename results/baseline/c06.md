## Summary
This PR reorders parameters in the `compose` function (swapping `onError` and `onNotFound` positions) and implements error handler propagation when sub-apps are mounted via `app.route()`. The main risk is that the parameter reordering is a breaking change to the `compose` API that could silently break callers passing positional arguments.

## Findings (5)

### 🔴 High — src/compose.ts:12 — breaking-change

The `compose` function signature changed from `(middleware, onNotFound?, onError?)` to `(middleware, onError?, onNotFound?)`. This is a breaking change for any external callers using positional arguments. While the PR updates internal call sites and tests, external consumers of this exported function will silently pass the wrong handler to the wrong parameter.

→ Check: Verify whether `compose` is part of the public API or only internal. If public, this requires a major version bump and migration guide. Check if there are any external packages or examples that call `compose` directly.

### 🟡 Medium — src/hono.ts:124 — api-contract

The logic `app.errorHandler === errorHandler` uses reference equality to detect whether a sub-app has a custom error handler. This is fragile: if a sub-app's errorHandler is reassigned or if the default `errorHandler` function reference changes (e.g., due to module reloading or bundling), the comparison will fail and the custom handler won't be wrapped. The test at line 960 shows the expected behavior, but the implementation is brittle.

→ Check: Consider adding a flag (e.g., `_hasCustomErrorHandler`) to track whether a custom error handler was set, rather than relying on reference equality. Verify this works correctly across different bundling/module scenarios.

### 🟡 Medium — src/hono.ts:124 — unhandled-edge-case

When wrapping a route handler with `compose([r.handler], app.errorHandler)`, the composed function is expected to catch errors from `r.handler` and pass them to `app.errorHandler`. However, if `r.handler` is async and rejects, the error handling depends on the `compose` implementation correctly catching and forwarding the error. The test at line 960 covers this, but there's no explicit verification that async errors in sub-app handlers are caught and routed to the sub-app's error handler.

→ Check: Manually trace through the `compose` function to confirm it properly catches errors from async middleware and invokes the error handler. Verify the test at line 960 (`sub.get('/error')`) actually exercises the error path.

### 🟡 Medium — src/hono.ts:113 — test-gap

The new test for `notFound` at line 980 expects `/sub/implicit-404` to be handled by the app's notFound handler, not the sub-app's. However, the PR only implements error handler propagation, not notFound handler propagation. The test may pass for the wrong reason (default behavior), but the comment suggests an expectation that isn't explicitly implemented.

→ Check: Verify that the notFound test expectations are correct. If sub-app notFound handlers should also be propagated (like errorHandlers), implement that logic. If not, clarify why errorHandler and notFound are treated differently.

### 🟢 Low — src/compose.test.ts:158 — test-gap

Test updates pass `undefined` as the second parameter (onError) when only onNotFound is needed. While this works, it's not explicit about the parameter order change. A comment explaining the parameter reordering would help reviewers and future maintainers.

→ Check: Consider adding a comment in the test file or compose.ts documenting why the parameter order was changed and the migration path for callers.
