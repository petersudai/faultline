## Summary
This PR adds a fallback mechanism for environments where `Response.clone()` is not supported (e.g., AWS Lambda). When cloning fails, it reads the response body into an ArrayBuffer and regenerates the ETag. The `generateDigest` function is refactored to accept either a ReadableStream or ArrayBuffer.

## Findings (5)

### 🔴 High — src/middleware/etag/index.ts:102 — data-loss

After calling `res.arrayBuffer()`, the response body stream is consumed and cannot be read again. The fallback then creates a new Response with the buffer, but the original response body is already exhausted. If the middleware is used in a chain where downstream handlers or the final response sender expects to read the body, it will get an empty stream.

→ Check: Verify that after the fallback path executes, the response body is still readable by downstream code. Test with a middleware chain where another handler tries to read the response body after etag middleware.

### 🟡 Medium — src/middleware/etag/index.ts:101 — error-handling

The catch block catches all errors from `res.clone()`, but `res.clone().body` could also throw if the response object is malformed. The broad catch may mask other unexpected errors. Additionally, if `res.arrayBuffer()` itself throws, it will be caught and silently treated as a fallback scenario, which may not be the intended behavior.

→ Check: Consider catching only the specific error from `clone()` (e.g., check if clone is undefined or throws a specific error type) rather than all exceptions. Verify that `res.arrayBuffer()` errors are handled appropriately.

### 🟡 Medium — src/middleware/etag/index.ts:110 — api-contract

The fallback path reassigns `c.res` to a new Response object. This could break if downstream middleware or handlers have already captured a reference to the original response object or rely on response object identity. The new Response may not preserve all properties or behavior of the original.

→ Check: Verify that reassigning `c.res` does not break any downstream middleware or response handling. Check if there are any tests that verify response object identity or properties are preserved.

### 🟢 Low — src/middleware/etag/index.test.ts:158 — test-gap

The test mocks `clone()` to throw an error, but it doesn't verify that the fallback path actually executes or that the response body is still readable after the middleware. The test only checks that status, ETag, and text are correct, but doesn't confirm the fallback was triggered.

→ Check: Add a test that verifies the fallback path is actually taken (e.g., by checking that `clone()` was called and failed). Also test that the response body can be read multiple times if needed by downstream handlers.

### 🟢 Low — src/middleware/etag/digest.ts:12 — api-contract

The function signature changed from accepting `ReadableStream<Uint8Array> | null` to `ReadableStream<Uint8Array> | ArrayBuffer | null`. This is a breaking change for any external callers of `generateDigest`. However, since this is an internal utility (not exported in the main API), the risk is lower.

→ Check: Confirm that `generateDigest` is not part of the public API or used by external consumers. If it is exported, this is a breaking change that should be documented.
