## Summary
This PR adds support for greedy route parameters with subsequent static components (e.g., `/:dirs{.+}/file.html`). The implementation uses lookahead assertions in regex patterns and a queue-based search mechanism. The changes are well-tested, but there is a potential cache key collision issue in getPattern() when the `next` parameter varies.

## Findings (2)

### 🟡 Medium — src/utils/url.ts:62 — unhandled-edge-case

The cache key uses `${label}#${next}` which becomes `label#undefined` when next is undefined. This could cause cache collisions if the same pattern is used in different contexts (with and without a next component). The cache should distinguish between these cases more robustly.

→ Check: Verify that patterns registered in different route contexts (with/without subsequent static components) don't incorrectly share cached regex patterns. Test a scenario like registering both `/:id{[0-9]+}` and `/:id{[0-9]+}/details` in the same router.

### 🟢 Low — src/router/trie-router/node.ts:180 — other

The component count calculation uses `m[0].match(/\//)?.length ?? 0` to count slashes. This counts the number of slash matches, but the logic assumes each slash represents one path component. This is correct for normal paths but could be fragile if paths contain encoded slashes or other edge cases.

→ Check: Verify that the slash-counting logic handles edge cases correctly, particularly with URL-encoded slashes (%2F) or unusual path structures.
